## À reprendre en priorité

La revue de la tâche 11 a jugé **le code de production correct**. Ce qui reste ouvert concerne le diagnostic et l'outillage de test, et c'est décrit en détail dans `.superpowers/sdd/progress.md`, section Task 11. En résumé :

1. **La vraie cause d'une intermittence des tests de bout en bout a été identifiée mais pas corrigée.** Dans `e2e/admin-produits.spec.ts`, `afterAll` s'exécute **une fois par worker** et supprime les deux produits de test, quel que soit le test joué : le worker le plus rapide efface les données des autres. Le contournement en place (`mode: 'serial'`) masque le bug. Correctif : un slug par test, un nettoyage par test tolérant à l'absence, puis retrait du mode série.
2. **Un commentaire trompeur** dans ce même fichier attribue l'intermittence à `output: 'standalone'`. C'est faux — `next start` n'émet qu'un avertissement et sert le build normal. À retirer, sinon il enverra le prochain mainteneur au mauvais endroit.
3. **`vitest.config.ts` porte `fileParallelism: false`**, ce qui sérialise les dix-sept fichiers de la suite pour arbitrer un conflit entre **deux** assertions qui vérifient l'état global de `public/uploads/`. Faire porter chaque assertion sur ses propres fichiers, puis rétablir le parallélisme.
4. **Le message « image illisible » n'est atteint par aucun test** : le test envoie un `application/pdf`, rejeté bien avant par la validation de type. Il faut un type MIME accepté avec un contenu invalide.

Une branche `wip/task-11-correctifs` contient une tentative de correction **interrompue et cassée** (22 tests en échec). Elle est conservée pour référence seulement — **ne pas la fusionner**. Repartir des consignes ci-dessus est plus sûr que de la reprendre.

## Pièges de l'environnement

- **Le conteneur PostgreSQL s'arrête tout seul** (instabilité Docker Desktop connue). Symptôme : une vingtaine de tests en échec et une trentaine ignorés, sur du code pourtant vert. Réflexe : `docker compose -f docker/compose.dev.yml up -d` avant de suspecter le code.
- **`next dev` ne sert rien sur cette machine** : il démarre, n'émet aucun log, ne répond jamais. Playwright vise `npm run start` ; un `npm run build` doit donc précéder.
- **`npm install` prend 10 à 20 minutes.** Windows Defender analysant `node_modules` est le suspect principal — une exclusion sur `D:\Projet` réglerait probablement le problème.
- **Ne jamais lancer deux `npm install` en parallèle** : cela a corrompu `node_modules` deux fois.
- **Prisma épinglé en 6.19.3** ; la v7 supprime `url = env("DATABASE_URL")` dans le schéma.
- **zod est en version 4** : `_def.type`, et non `_def.typeName` comme en v3.
- `prisma migrate dev` échoue sans terminal interactif dès qu'il doit avertir. Contournement : `prisma migrate diff` puis `prisma migrate deploy`.
- Node exécute le TypeScript nativement (`node --experimental-strip-types`) : `tsx` est inutile.
- Configuration du serveur de prévisualisation : `D:\Projet\.claude\launch.json`, entrée `summerclub`.

## Convention de sécurité, valable pour toutes les tâches d'administration

Un layout ne suffit pas : il n'est pas ré-exécuté à chaque navigation, ne s'exécute pas sur une route inexistante, et ne protège ni les Server Actions ni les Route Handlers. **Toute page, toute action serveur et tout Route Handler sous `/admin` doit appeler `requireAdmin()` lui-même.**
