## Ce qui a été livré depuis la passation précédente

### Le renommage des identifiants français (2026-09-03/04, hors tâche)

Sur ordre du propriétaire — « le code n'est pas valide si du français dans le code » —, tout le
code de `src/`, `tests/`, `e2e/`, `prisma/seed.ts` et `tools/` est passé en anglais : sept
énumérations **et leurs valeurs**, ~55 colonnes, 27 fichiers déplacés, 138 identifiants exportés,
42 internes. La migration a été **écrite à la main en `RENAME`** après rejet du diff de
`prisma migrate diff`, qui proposait des `DROP`/`ADD COLUMN` — donc destructeurs sur des données
déjà écrites.

Ce qui n'a pas bougé et ne bougera pas : **les segments de route en français**
(`admin/produits`, `connexion`, `boutique`) et **tous les libellés**. `docs/RENOMMAGE.md` reste
la table de correspondance complète — c'est une **trace de ce qui a été appliqué, pas une liste
de travail en attente**.

**La règle qui en découle est un critère de validité, pas un goût** : un identifiant français
introduit — variable locale comprise — rend la contribution invalide et la tâche n'est pas
validée, quelle que soit la qualité du reste. Sans exception d'ancienneté.

### Tâche 15 — la page d'accueil

Cinq sections (spec § 8) dans le groupe `(storefront)`. **Le gabarit `create-next-app` a
disparu** : `src/app/page.tsx` et ses cinq SVG orphelins sont supprimés, et le lien de marque de
l'en-tête n'atterrit plus sur la page de démarrage de Next.js.

Trois points que la revue devra regarder en priorité, parce qu'ils ne sont pas dans le brief :

- **`productPathsToRevalidate` publie désormais `/`.** La sélection de l'accueil lit
  `listProducts` et la page est statique : sans cette entrée, un produit désactivé, renommé ou
  remisé y restait jusqu'à cinq minutes. C'est le jumeau exact du défaut trouvé sur la fiche à
  la revue de la tâche 14 (`docs/CONVENTIONS.md` § 4, règle 3 : après un cas corrigé, chercher
  son symétrique). Prouvé par mutation, build et bout en bout refaits.
- **`Reveal` a deux replis.** Le brief l'annonce « en CSS pur » puis en donne une implémentation
  à `IntersectionObserver` — contradiction tranchée en gardant l'observateur, mais une section
  qui ne s'affiche *que* sur intersection disparaît entièrement là où le mécanisme manque. Sans
  l'API : contenu visible, sans animation. Sans JavaScript du tout : une règle `<noscript>` de
  la page force l'opacité des conteneurs `data-reveal`. **Ce second repli n'a jamais été vérifié
  dans un vrai navigateur, JavaScript désactivé.**
- **`listPinnedReviews` exige épinglé ET publié.** Un avis peut porter le premier sans le
  second ; l'invariant se ferme donc aussi côté lecture, pas seulement dans l'action de
  modération.

## Pièges de l'environnement

### Sur la machine de la propriétaire (Windows + Docker Desktop)

- **Le conteneur PostgreSQL s'arrête tout seul.** Symptôme trompeur : une vingtaine de tests
  échouent d'un coup comme s'il y avait une régression. Réflexe, AVANT de suspecter le code :
  `docker exec docker-db-1 pg_isready -U summerclub -d summerclub`, puis
  `docker compose -f docker/compose.dev.yml up -d`. Une affirmation « la branche est cassée » a
  déjà été portée à tort pour cette seule raison.
- **`npm install` prend 10 à 20 minutes** et ne doit jamais être lancé deux fois en parallèle
  (`node_modules` corrompu deux fois). Windows Defender analysant `node_modules` est le suspect.
- Configuration du serveur de prévisualisation : `D:\Projet\.claude\launch.json`, entrée
  `summerclub`.

### Dans un conteneur cloud (constaté le 2026-09-21)

Une session distante **ne reçoit qu'un clone du dépôt** : ni `node_modules`, ni `.env`, ni
démon Docker — donc pas de base. Remise en route vérifiée, dans cet ordre :

```bash
npm install                                        # quelques dizaines de secondes ici
pg_ctlcluster 16 main start                        # PostgreSQL 16 est installé, à l'arrêt
su postgres -c "psql -c \"CREATE ROLE summerclub LOGIN PASSWORD 'dev' SUPERUSER\""
su postgres -c "createdb -O summerclub summerclub"
# puis un .env local (non versionné) pointant sur le port 5432, PAS le 5433 du compose
npx --no-install prisma generate && npx --no-install prisma migrate deploy
npx --no-install prisma db seed
```

Les deux lignes `CREATE ROLE` / `createdb` échouent sans dommage si la base survit déjà au
redémarrage du conteneur : vérifiez avec `pg_isready` avant de conclure à autre chose.

Deux écarts à garder en tête quand on lit des résultats obtenus ainsi :

- **PostgreSQL 16 du système**, port 5432, au lieu du `postgres:17-alpine` de
  `docker/compose.dev.yml` sur le 5433. Les migrations passent, mais ce n'est pas la même
  version de moteur.
- **Playwright réclame un build Chromium que le conteneur n'a pas** (1234 demandé, 1194
  présent). `npx playwright install` est proscrit dans cet environnement ; la suite a tourné via
  une surcharge **non versionnée** pointant `executablePath` sur
  `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`, supprimée après usage. Rien d'autre de
  la configuration n'a été touché.

### Valables partout

- **`next dev` ne sert rien sur ces machines** : il démarre, n'émet aucun log, ne répond jamais.
  Playwright vise `npm run start` ; un `npm run build` doit donc précéder.
- **Prisma épinglé en 6.19.3** ; la v7 supprime `url = env("DATABASE_URL")` dans le schéma.
- **zod est en version 4** : `_def.type`, et non `_def.typeName` comme en v3.
- **vitest est en version 4** : `environmentMatchGlobs` a disparu, remplacé par `test.projects`
  (`vitest.config.ts` : un projet `node` pour les `.test.ts`, un projet `jsdom` pour les
  `.test.tsx`).
- `prisma migrate dev` échoue sans terminal interactif dès qu'il doit avertir. Contournement :
  `prisma migrate diff` puis `prisma migrate deploy`.
- Node exécute le TypeScript nativement (`node --experimental-strip-types`) : `tsx` est inutile.
- **`AGENTS.md` est réécrit par `next dev`** : ne comptez pas dessus, le point d'entrée durable
  est `CLAUDE.md`.
- `next start` ignore `output: 'standalone'` (simple avertissement, le build normal est servi).

## Dettes ouvertes

### Rattachées à une tâche future

- **Tâche 17** : l'interface `PaymentProvider` n'existe que dans le plan. C'est elle qui portera
  l'inversion de dépendance du paiement — citée dans `docs/CONVENTIONS.md` § 3 comme intention,
  **pas** comme exemple réel.
- **Tâche 18** : le **numéro WhatsApp Business n'est écrit nulle part** et ne s'invente pas — un
  numéro approximatif ouvrirait une conversation avec une inconnue, qui recevrait les commandes.
  La page d'accueil le lit dans `WHATSAPP_NUMBER` (voir `.env.example`) et **ne rend aucun lien
  tant qu'il est absent ou mal formé**. La tâche 18 aura besoin du même numéro, et devra
  normaliser les formes locales (« 032 46 182 90 ») vers la forme internationale ; le garde de
  `call-to-action.tsx` refuse tout le reste au lieu de le réparer.
- **Tâche 19** : les gestionnaires de webhook se créent sous `api/payments/[provider]/webhook/`,
  **pas** `api/paiement/…` comme l'écrit le plan — et une URL de webhook communiquée à un
  prestataire coûte cher à changer après coup (`docs/CONVENTIONS.md` § 1, cas 3).
- **Tâche 22 — `advanced.ipAddress` de Better Auth** reste à configurer avec Caddy. Sans quoi le
  seau de limitation de débit est **global** : un visiteur anonyme peut verrouiller la connexion
  de l'administratrice. C'est aussi ce qui avait imposé, un temps, un plafond de workers à
  Playwright.
- **Tâche 22 — cache ISR des slugs inconnus.** `/boutique/[slug]` est rendu statiquement ; tout
  slug bien formé mais inconnu est rendu (404) **puis écrit sur le disque** sans éviction. Un
  trafic anonyme sur des slugs aléatoires remplit donc le disque du serveur. Ce qui est déjà
  fermé : la liste blanche de `src/domain/slug.ts` coupe le coût SQL des slugs mal formés (un
  NUL faisait lever PostgreSQL, 500 au lieu de 404). Ce qui reste : **limitation de débit au
  reverse proxy sur `/boutique/*`**, et, si elle ne suffit pas, un `cacheHandler` borné.
  `dynamicParams = false` a été écarté — il rendrait invisibles les produits créés après le build.

### Héritées de la tâche 15, à arbitrer

- **`public/hero-1200.avif` est un aplat de `--clay` en 1200×1500, pas une photographie.** Le
  dépôt n'en contient aucune et la prise de vue est une dépendance externe
  (`public/guide-photo.md`). L'image est donc **décorative** (`alt=""`, `aria-hidden`) : **la
  vraie photo devra arriver avec son texte alternatif**, et `aria-hidden` disparaître. C'est la
  seule image `priority` du site — elle porte le LCP.
- **La sélection de l'accueil est la tête du catalogue** (`displayOrder`, huit pièces), pas une
  colonne « mis en avant ». La spec § 8.3 dit « choisis en admin » : vrai au sens de l'ordre
  d'affichage, faux au sens d'un marquage dédié. Une vraie colonne serait un changement de schéma.

### Sans tâche assignée

- **Backlog V1.1** : conserver sur `OrderItem` la promotion appliquée et le prix avant remise.
  La ligne ne garde aujourd'hui que `nameSnapshot`, `unitPriceSnapshot` et `quantity` : impossible
  de savoir a posteriori quelle promotion a servi, ni à partir de quel prix.
- **Backlog V1.2** : la table `expenses` de la spec § 5 n'appartient à aucune tâche V1.0.
- **Pas d'écran catégories** : en créer une passe encore par la base.
- **Gardes d'idempotence des avis lus hors transaction** — acceptable sur un écran
  mono-utilisatrice, pas au-delà.
- **Intermittence de bout en bout vue une fois** (bouton bloqué sur « Enregistrement… » 30 s),
  non reproduite en quatre exécutions. Si elle revient, chercher du côté de la revalidation
  concurrente de la page statique `/` — **et pas du côté d'un retry ou d'une sérialisation**.
